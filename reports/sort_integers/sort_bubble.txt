--- Usefulness & limitations of this evaluation ---
Useful for:
  1. Grading programming labs at scale (CS1/CS2 courses)
     Example: 300 students submit 'sort n integers'. The agent grades all of them overnight
     under identical limits. A student whose bubble sort times out on n = 100000 receives
     the failing input size, the measured O(n^2) growth curve and the hottest loop line,
     instead of a bare 'time limit exceeded'.
     Benefit: Consistent, explainable grades in minutes; teaching assistants only look at
     flagged or borderline submissions.
  2. Coding-interview and hiring screens
     Example: A company runs 500 candidate submissions for an 'add two integers safely'
     task. The agent ranks them by correctness, overflow handling and memory safety, and
     every rejection is backed by a concrete failing input such as '2147483647 1'.
     Benefit: Fast first-round filtering where every decision can be justified metric by
     metric.
  3. Plagiarism and LLM-copy triage
     Example: Two submissions reach a similarity of 0.93 (threshold 0.85) even though every
     variable was renamed and every comment rewritten. The agent flags the pair with the
     matching line ranges, so the instructor inspects 2 files instead of 300. A third
     submission matches a solution generated by an LLM for the same statement and is flagged
     as a suspected LLM copy.
     Benefit: Review time goes only to suspicious cases, and the evidence (lines,
     similarity) is already prepared.
  4. Self-check before the deadline / continuous integration for assignments
     Example: A student's qsort solution passes the visible sample, but the agent's
     generated boundary case '2 / 0 -2147483648' shows that the comparator 'return a - b'
     overflows. The minimized counterexample and the suggested fix arrive before the student
     submits.
     Benefit: Finds bugs that fixed test suites miss and teaches with the smallest input
     that breaks the program.
Limits of this report:
  1. Testing cannot prove correctness
     Example: add_magic_value.c prints 0 whenever the first number is 4242. It passes 10/10
     hidden tests and all 18 generated edge cases and is graded 97.9/100, because neither
     the tests nor the generators happen to produce 4242.
     Mitigation: Larger random budgets and instructor-specified 'must-test' values reduce
     the risk but never remove it; suspicious special-casing still needs a human reader.
  2. Complexity is estimated from measured operation counts, not proven
     Example: sort_memmove_insertion.c finds each insertion point by binary search and
     shifts with memmove(). Its O(n^2) work happens inside libc, which gcov does not
     instrument, so the executed-line count grows like n log n, the agent reports 'O(n log
     n) confirmed' and grades it 99.8/100. Likewise a quicksort with a first-element pivot
     is O(n log n) on the random inputs used for measuring, but O(n^2) on sorted input.
     Mitigation: Include adversarial (sorted) inputs and a large hidden test that only an
     efficient solution passes within the time limit.
  3. Similarity-based copy detection has false positives and false negatives
     Example: For 'add two integers', two honest solutions are almost the same token stream;
     the agent avoids flagging them only because of reference-code subtraction and the
     minimum-shared-fingerprints rule. Conversely, a student who takes an LLM answer and
     rewrites loops (for -> while), splits functions and reorders statements drops below
     0.85 and is not flagged. When a pair is flagged, both students are flagged: the agent
     cannot tell who copied whom.
     Mitigation: Flags are review signals, never automatic verdicts; the instructor decides
     after reading the matched lines.
  4. Verdicts depend on the platform and on external models
     Example: On Windows (MinGW) `long` is 32 bits, so a solution that sums into `long`
     overflows and fails tests that pass on Linux; ASan is unavailable there, so
     memory_safety falls back to UBSan trap mode and a leaking program loses no points. The
     LLM readability score can also change after `ollama pull` updates the model weights,
     and a program running at 0.95-1.05 s CPU can flip between AC and TLE across machines.
     Mitigation: Run official grading in the provided Linux/Docker image, keep the LLM
     response cache with the course records, and keep the hidden tests far from the time
     limit; every report records tool versions and hashes.
